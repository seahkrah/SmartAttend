# Adopt PostgreSQL row-level security for tenant data

Date: 2026-10-02. Status: accepted. Supersedes the paragraph of
[2026-09-30-keep-express-platform.md](2026-09-30-keep-express-platform.md)
that declined RLS.

## Decision

Tenant isolation is enforced twice: by the application, as before, and by
PostgreSQL, so that one forgotten `WHERE tenant_id` cannot become a
cross-tenant leak. The product owner made this a requirement on 2026-10-01.

## How

1. **Policies.** Every table with a `tenant_id` column has RLS enabled and
   forced, with one policy:
   `USING / WITH CHECK (tenant_id = (SELECT app_current_tenant()) OR (SELECT app_is_system()))`.
   `app_current_tenant()` reads the session setting
   `app.tenant_id`; empty means no tenant, so no rows.
2. **Roles.** `jjelotech_app` is a NOLOGIN group with DML rights on every
   table, `NOBYPASSRLS`, and owning nothing. The API's runtime login
   (`APP_DATABASE_URL`) is a member. `jjelotech_system` is a NOLOGIN group
   whose members pass the policy's system clause: the migration owner, and
   the API's system pool (`DATABASE_URL`). Migrations run as the owner.
3. **Context.** Express middleware puts `{ tenantId, userId }` in an
   `AsyncLocalStorage` once the tenant is resolved. The pool wrapper in
   `db/connection.ts` sets `app.tenant_id` and `app.user_id` on every
   connection it hands out whenever they differ from what that connection
   last held. A connection returned to the pool mid-transaction is destroyed.
   Because this sits in the pool, all ~1,300 existing call sites (`query`,
   `getConnection`, `client.query`) become tenant-bound without being
   rewritten one by one. `withTenant(ctx, fn)` does the same for code
   outside a request.
4. **System access** is explicit: `runAsSystem(reason, fn)` routes to the
   system pool. It is allowed only in identity, control-plane, migration and
   cross-tenant job modules (allow-list in
   `scripts/checks/no-raw-query.mjs`). Direct use of the `pg` pool or
   `pg.Client` outside `src/db/` fails the lint.
5. **Views** are `security_invoker`; `SECURITY DEFINER` functions in
   `public` are not allowed.

## Why the pool, not a rewrite of every query

The brief asks for "a single data-access layer that is the only way routes
reach tenant data". Wrapping the pool's `connect()` is that layer: there is
no other way to obtain a connection. Rewriting 1,300 call sites by hand
would multiply the chance of a mistake, and would leave the old path open
unless the pool were wrapped anyway.

## What RLS does not do here

It backs up correct, parameterised code against **omissions**. It is not a
defence against SQL injection: injected SQL running as the app role could
call `set_config('app.tenant_id', …)`. That is handled by parameterising
everything, which `validate-sql` and Semgrep check.

## Compatibility

If `APP_DATABASE_URL` is not set, both pools use `DATABASE_URL` and behave
as before: the owner is a member of `jjelotech_system`, so nothing is
filtered. CI and production set it; the scorecard's `runtime-role` gate
fails without it. If the migration cannot create roles (the owner lacks
`CREATEROLE`), it enables RLS but does not force it, and says so with a
warning; `docs/operations/deployment.md` gives the manual steps.

PostgreSQL 15 or later is required (`security_invoker` views). The
deployment uses 16.
