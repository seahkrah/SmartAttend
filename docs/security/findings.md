| 12 | Medium | A superadmin's `X-Tenant-Id` went into the request context unchecked, although the code comment said the tenant must exist: a malformed value produced a 500 from SQL, and a made-up UUID returned 200 with empty data. Nor was the switch recorded anywhere. | Independent audit, Phase 0 | Fixed. The value must be a UUID naming an existing tenant (404 otherwise; regression checks in `crossTenantAudit`). | 13 | Medium | AES-256-GCM decryption of TOTP secrets (`auth/mfa.ts`) and biometric templates (`biometrics/templateCrypto.ts`) did not pin the authentication-tag length. Trivy: 0 HIGH/CRITICAL in both. Both images still migrate, boot and serve as CI checks. |
| 15 | Info | The working-tree secret scan reported 39 findings, all in `docs/archive/`: `YOUR_TOKEN` placeholders in curl examples and truncated JWT prefixes. | 16 | Info | Three Semgrep `tainted-sql-string` results were false positives: an error message starting with the word "delete", and two UPDATEs whose column names come only from fixed allow-lists, with all values bound. | Semgrep | Suppressed inline with the reason beside each. |
| 17 | High | Tables that hold tenant-related records without a `tenant_id` column are outside row-level security. The Phase 1 audit showed what that means: from tenant A's context the runtime role read 134 users, password hashes included, and could update 5 of tenant B's users. The tables are `users`, the membership and session tables, drift and attendance history, and: `incidents` and its child tables (scoped by `affected_tenant_id`), `school_user_associations` / `corporate_user_associations`, and the role and approval tables. Their isolation rests on application code alone. | Phase 1 survey (76 tables without `tenant_id`) | **Fixed in Phase 2** (migrations 074, 075). Accounts are under forced RLS: visible to the runtime role only for the person themselves, members and applicants of the tenant in force, and accounts created in it. The runtime role has no privilege on `password_hash`; passwords are checked and set by the sign-in code on the system pool. Membership, approval and entity tables get the tenant policy on their tenant column; sessions, links and two-factor rows follow their account; failed sign-ins are system-only. Incidents follow `affected_tenant_id` and their child tables the incident; per-person drift and escalation records follow the person; 24 control-plane and unused legacy tables are system-only. `identityIsolation` (32 checks) tests it as the runtime role and fails on any table naming an account that is neither under a policy nor decided. |
| 18 | Low | When a KMS is configured, face templates sealed earlier under `BIOMETRIC_TEMPLATE_KEY` still open under it, and are not re-encrypted under the tenant's data key. | Phase 1 | **Open.** A re-encryption job, with documents and other personal data, in Phase 4. |
| 19 | High | Break-glass could be bypassed: with no grant, a superadmin could appoint a tenant administrator with `handover: true`, take the setup link, sign in and read the tenant's data, invisible to the tenant. Changing a tenant user's email and then resetting the password was a second route. | Independent audit, Phase 1 | Fixed. A handed-over setup link (on appointment or re-issue) and an email change on a tenant account need an open grant for that tenant; each is logged under it and written to the tenant's audit trail. `breakGlass.e2e.py` covers both paths, with and without a grant. |
| 20 | Medium | The runtime role could insert forged break-glass grants, and delete grants, access-log rows and its own tenant's data keys. | Independent audit, Phase 1 | Fixed (migration 073): grants are read-only to the runtime role; the access log is insert-only; data keys cannot be deleted by it. Checked by `rlsNoContext`. |
| 21 | Medium | 87 single-column foreign keys between tenant tables had no same-tenant guard, and PostgreSQL checks foreign keys without RLS. | Independent audit, Phase 1 | Fixed (migration 073): `app_apply_same_tenant_guards()` generates guards from the catalog; all 115 references are covered. The `sameTenantGuards` gate and `rlsNoContext` fail if one is missing (shown with a guard dropped). |
| 22 | Medium | By design, SQL running as the runtime role can call `set_config('app.tenant_id', …)`: RLS backs up correct code, it does not stop SQL injection. The lint missed `set_config($1, …)` and `SET SESSION app.*`. | Independent audit, Phase 1 | Lint extended to any `set_config(`, `SET/RESET [SESSION|LOCAL] app.*`, and `withTenant` outside the tenant middleware. The injection boundary remains parameterised SQL (validate-sql, Semgrep). |
| 23 | Low | The superadmin router runs on the system pool, so `/superadmin/users` lists every tenant's users' names, emails and phones to a superadmin. | Independent audit, Phase 1 | Accepted for the control plane, which is platform-wide by design; it stays in the control-plane audit log. To revisit with SSO and role separation in Phase 2. |
